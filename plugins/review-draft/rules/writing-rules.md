# 成果物の日本語規範

Linear / GitHub / esa に投稿する文章に共通して適用する. 投稿先ごとの規約は `target-rules.md` を見る.

各項目の見出しがそのまま指摘時の項目名になる. 引用と項目名を必ず添えて報告する.

## 1. 記載範囲

**非自明な理由だけを書く.** コードコメントも成果物の文章も, 読めばわかることを書かない. 書く価値があるのは, 読んでも分からない「なぜそうしたのか」だけである.

**途中の試行を残さない.** 検討して捨てた案, 一度書いて直した記述, 試して駄目だった方法は残さない. 「最初は A を検討したが B にした」は, B の理由が A との対比なしに書けるなら不要である.

**PR description は最終的な挙動と, diff から読み取れないトレードオフだけを書く.** 差分を見れば分かることを日本語で言い直さない. 逆に, なぜこの設計にしたのか, 何を捨てたのかは diff に現れないので書く.

**マージされなかった状態に言及しない.** レビュー中に書き換えた実装, 途中の commit にあった挙動, 一度 push して戻した変更には触れない. PR description が説明するのはマージされる状態だけである.

**変更履歴を残さない.** 「(修正済み)」「~~取り消し線~~」「※ 当時の結論」「<details>変更履歴</details>」を書かない. 解決した項目は注記せず行ごと削除する. GitHub / Linear / esa には編集履歴が別にあるので, 本文に履歴を持たせる必要がない.

**却下案を残さない.** 設計判断は採用した理由だけを述べる. ただし既存実装との対比 (「既存の X はこうなっているので踏襲しない」) は既存コードの説明なので残してよい.

**タイトルが指す範囲を超えない.** 関連していても別の関心の作業は, 同じ文書に混ぜず別の issue / 手順書に分ける.

## 2. 読者の前提

**会話の文脈を混入させない.** 会話で聞かれたから否定した命題を成果物に残さない. 「どちらも API Gateway ではない」は, API Gateway がリトライするか聞かれた文脈からしか出てこない一文で, issue の読者には唐突である. 読者が自然に持つ疑問だけを扱う.

**チームが知っている基本構成を説明しない.** インフラの経路 (EventBridge から Lambda への非同期 invoke, API Gateway の proxy integration など), 使っているフレームワークの標準的な挙動, 社内の一般的な運用は既知として省く. 非自明な事実だけ明示する.

**節を唐突に始めない.** 節の冒頭で, なぜその節が必要なのかを述べる. 前の節との論理関係を接続表現で示す.

**後で参照しない固有名を出さない.** 一度しか出てこないファイル名・関数名・識別子は, 「仕様書」「金額計算のユーティリティ」のような一般的な言い方に置き換える. ただし読者が実際に開くパスや行番号は残す.

**ファイルパスを省略しない.** `...` で省略せず, 常にフルパスで書く. 読者がコピーして使えなくなる.

## 3. 回りくどい書き方

**否定してから言い直さない.** 「A は B ではない. C である.」を「A は C である.」の一文にする.

- 悪い: 「Duration は Redis だけの時間ではない. rate limiter なら Redis と SQS SendMessage の合計である.」
- 良い: 「Duration は, rate limiter なら Redis への読み書きと SQS SendMessage の合計である.」

否定が情報を運ぶ場合 (読者が誤解しそうな解釈を先に潰す) は残してよいが, その場合は否定の根拠を一文添える.

**体言止めで文章を始めない.** 名詞句だけの文で節や段落を開始しない.

- 悪い: 「期間は 2026-08-18 から 08-25 の 7 日間.」
- 良い: 「2026-08-18 から 08-25 の 7 日間を対象に, Duration を計測した.」

**予告で主張を包まない.** 「重要なのは〜である」「本節では〜を扱う」「〜について見ていく」を書かず, 主張をそのまま書く.

**同じ主張を言い換えて繰り返さない.** 場面を書いた直後にその要約を置かない. 一つの主張は一度だけ書く.

**接続や評価だけの文を置かない.** 「それ自体はよいことである」のような, 情報を運ばない一文を挟まない.

## 4. 語の正確さ

**製品名やサービス名を操作名に流用しない.** 何の時間・何の失敗を指しているかが読者に確定しない.

- 悪い: 「Redis の往復が数 ms」「この 2.3s が Redis 由来か」
- 良い: 「Redis への読み書き 1 回の往復が数 ms」「この 2,325.9ms が Redis への読み書き由来か」

同様に「予約」だけで済ませず「予約同時実行数」と書く.

**単位を全ての数値に付ける.** `10.6ms / 19.5ms` と書き, `10.6 / 19.5ms` のように片方を省略しない. 表のヘッダに単位があっても, セル内の各値に付ける.

**術語を統一する.** 一度導入した語で通す. `concurrency` と「同時実行数」, `10 秒` と `10s` を混在させない.

**術語の響きを持つ語を術語でない場面に流用しない.** 「経路」「並び」のような語を比喩として使わず, 普通の言い方で書く.

**慣用表現をひねった言い回しや, 指す内容が一意に決まらない比喩を使わない.**

## 5. 事実と推測の区別

**確認していないことを断定しない.** ログ・DB・コードで直接確認した事実と, そこから導いた推測を構造的に分ける. 推測には「と推定できる」「可能性がある」を付け, 何を確認していないのかも書く.

- 良い: 「Redis への読み書き 1 回は数 ms オーダーに収まっていると推定できる. 読み書きだけを切り出した計測値は無いので, ここは推定にとどまる.」

**推量を機械的に断定へ変えない.** 「かもしれない」「だろう」は, 根拠なく主張を弱めている場合だけ削る. 事実未確認の可能性, 読者が抱きそうな疑念, 反実仮想を表す場合は不確実性を保つ.

**因果を主張するときは機構を一文で示す.** 「A だと B になる」だけで理由を省略しない.

**検出・保証・解決を「必ず」できるかのように書かない.** 「〜しやすい」「〜が成り立つときに限り」と条件付きで述べる.

**異なるものを「同じ」とまとめない.** 区別すべき別々の決定・別々の原因を一括りにしない.

**挙げた例が主張の全体を支えているか確認する.** 支えないなら主張の範囲を例に合わせて狭める.

## 6. 文体

**常体で書く.** ですます調を使わない.

**句読点はカンマ (,) とピリオド (.) を使う.** 読点 (、) と句点 (。) を使わない.

**英語由来の技術用語は英語で書く.** コンテナではなく container, リファクタリングではなく refactoring.

**一文ごとに改行する.** 段落の区切りは空行で示す.

**ダッシュを地の文・見出しで使わない.** em ダッシュ (—), horizontal bar (―), 2 倍ダッシュ (——) を使わない. 同格の挿入は括弧に, 言い換えは二文に分けるか読点でつなぐ. 範囲を示す en ダッシュや英語の複合語は対象外.

**中黒 (・) を並列で使わない.** 単一の固有名詞の内部では使ってよい.

**イ形容詞に「です」を続けない.** 「難しいです」「多いです」が出たら, 文末だけ直さず前後の流れごと書き直す.

**太字を多用しない.** 誤読を防ぐ否定や節の帰結など, 論理の要所に限る. 一節に一, 二箇所まで.

**用語を初めて定義するときは太字にする.** 以後の言及は「」を使う.

## 7. 段落と論証

**一つの段落に一つのトピックだけ置く.** 調査・報告・検証・評価が混ざった長い段落は一歩ずつに分ける.

**段落の最初の文で, その段落が何の話かわかるようにする.**

**論証は一方向に進める.** 結論を出してから反論を処理し, 結論を言い直す構成にしない.

**譲歩や限定を置いたら, その後で論を進める.** 逆接で終えて宙吊りにしない.

**前方参照は論証が一段落した位置に置く.** 節の途中に「後述する」を挟んで流れを切らない.

**節の中心となる語は, 使う前に定義・対象範囲を述べる.**

## 8. 表とデータ

**表は論で参照する値だけに絞る.** 本文で一度も触れない統計値 (avg, p90 など) や属性 (memory size など) を並べない. 行が多いほど読者は何が要点か分からなくなる.

**表に入れるより地の文に置いた方がよい情報を見分ける.** 全ての行で同じ値になるもの, 一度しか参照しないものは地の文に移す.

**セル内に複数の統計値を詰めるときは, 各値に単位を付ける.**

**見積もりや換算値には, それが下限か上限か, 何を仮定したかを添える.**

## 9. 見出し

**内容を特定できる見出しにする.** その節が答える問い, または扱う対象を指す句にする.

**節の結論を言い切る「セリフ」にしない.** 見出しの時点で読者がオチを知る状態を避ける.

**手順だけを述べる見出しや情報量のない見出しにしない.** 「例に戻す」「まとめ」など.

**区切り線で二要素を詰め込まない.** 「種別──主題」の形にせず, 単一の自然な句にする.

## 10. LLM っぽい表現

論点を増やさず「ちゃんと書いている感」だけを付ける言い回しを使わない.

- **予告と総括**: 「重要なのは〜である」「本章では〜を扱う」「まとめると」「要するに」(直前の言い換えだけのとき), 「〜に他ならない」
- **正面から系**: 「正面から扱う」「正面から向き合う」— 中身の代わりに姿勢だけを宣言する
- **空虚な形容**: 「不可欠」「核心的」「鍵となる」「根本的な」「多角的」「包括的」「総合的」
- **空虚な動詞**: 「掘り下げる」「深掘りする」「言語化する」「触れる」「言及する」
- **接続の型**: 「〜において」「〜という側面から」「〜の観点から」(新情報なし), 「さらに」「また」「加えて」の連打
- **弱い緩和と称賛**: 根拠なく主張を弱める「〜と言えるだろう」, 中身のない強調の「非常に」「極めて」「大いに」

## 11. Markdown の構造

**隣接する list を空行だけで区切らない.** Markdown は空行を挟んでも同じ marker の list を継続する. 別の list のつもりで並べても 1 つの list として描画される. 「対象は 2 つある」と書いた直下に 2 項目の list と 3 項目の list を空行だけで並べると, 読者には 5 項目の list に見える. 切るには見出しか段落を挟む.

**list 項目の継続行はインデントを揃える.** 1 項目が複数行にわたるとき, 2 行目以降を字下げしないと別の段落として切れる.

**表のセル内で改行しない.** 1 セルに複数の文を入れたくなったら, その情報は地の文に移す.
