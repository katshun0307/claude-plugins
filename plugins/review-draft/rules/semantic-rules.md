# 成果物の規範 (hook 用の圧縮版)

外部に出す日本語の文章が満たすべき規範のうち, 機械判定できないものだけを並べる.
文体 (常体, カンマとピリオド, ダッシュ, 中黒) と Markdown の構造は
`~/.claude/hooks/review-draft-gate.py` が同じ本文を検査済みなので, 重複して指摘しない.
全文は `~/.claude/hooks/review-draft/writing-rules.md` にある.

## 1. 記載範囲

- 読めば分かることを書かない. 書く価値があるのは非自明な「なぜそうしたのか」だけである.
- 検討して捨てた案, 途中の試行, 一度書いて直した記述を残さない.
- 変更履歴を残さない. 解決した項目は注記せず行ごと削除する.
- マージされなかった状態や, レビュー中に書き換えた実装に言及しない.
- タイトルが指す範囲を超えた作業を同じ文書に混ぜない.

## 2. 読者の前提

- 会話の文脈を混入させない. 会話で聞かれたから否定した命題は, 読者には唐突である.
- チームが知っている基本構成 (インフラの経路, framework の標準的な挙動, 社内の運用) を説明しない.
- 節を唐突に始めない. なぜその節が必要なのかを冒頭で述べる.
- 後で参照しない固有名を出さない. 一度しか出ない識別子は一般的な言い方に置き換える.

## 3. 回りくどい書き方

- 否定してから言い直さない. 「A は B ではない. C である.」は「A は C である.」にする.
- 体言止めで文や節を始めない.
- 予告で主張を包まない. 「重要なのは」「本節では」を書かず主張をそのまま書く.
- 同じ主張を言い換えて繰り返さない. 情報を運ばない接続や評価だけの文を置かない.

## 4. 語の正確さ

- 製品名を操作名に流用しない. 「Redis の往復」ではなく「Redis への読み書き 1 回の往復」と書く.
- 単位を全ての数値に付ける. 表のヘッダに単位があってもセル内の各値に付ける.
- 術語を統一する. `concurrency` と「同時実行数」, `10 秒` と `10s` を混在させない.

## 5. 事実と推測の区別

- 確認していないことを断定しない. 推測には「と推定できる」を付け, 何を確認していないかも書く.
- 因果を主張するときは機構を一文で示す.
- 検出・保証・解決を「必ず」できるかのように書かない.
- 区別すべき別々の決定・別々の原因を「同じ」と一括りにしない.

## 6. 構成

- 注意点が複数あるときは箇条書きの列挙で済ませず, 小見出しで章立てする.
  見出しはリスクや事象を特定する句にする (例: 「ログの prefix を消す hook が空振りしうる」).
- 調査時点に依存する情報 (最新推奨バージョンなど) は調査日を明記する.
- 表は同じ列に同じ種類の値だけを置く.

## 投稿先ごとの規約

- **Linear issue**: 着手時の判断に使う情報だけを書く. 既存 issue の参照は `ABC-123` のような識別子だけを書き, URL を併記しない.
- **GitHub PR description**: `## Why` `## How` `## 動作確認` `## 参照ドキュメント` の見出しは規約なので, 見出しの付け方の規範より優先する. ファイルごとの変更を列挙せず設計方針だけを書く. `Closes #1234` のように issue を自動クローズする書き方をしない.
- **GitHub のレビューコメント参照**: コメント ID だけでなく完全な URL を書く.
- **esa 記事**: タイトルに `#` を入れない. 以降がタグとして解釈されタイトルが切れる.

## 指摘してはいけないこと

- 規範に項目が無い言い回しの好み.
- 外部の事実が間違っているという断定. 元データを持たないので判定できない.
  ただし本文の中だけで閉じる矛盾 (表の値と地の文の値が違う, 前提と結論が食い違う) は指摘してよい.
